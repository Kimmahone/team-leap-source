## 1. 왜 실행계획(1)에서 전환하는가

06 실행계획(1)의 목표는 「경북 학령인구 데이터 플랫폼」 프로토타입이었고, 그 계획은 지금도 옳다. 문제는 전제다.

```
data/raw/        0B
data/processed/  0B
```

**데이터가 한 건도 없다.** 프로토타입 `index.html`은 5개 화면이 다 돌아가지만, 표시되는 모든 수치는 코드가 생성한 더미다. 이 상태에서 8월을 더 쓰면 "더 예쁜 더미"가 나올 뿐이다. 대시보드의 가치는 화면이 아니라 **실제 데이터 + 검증된 예측**에 있고, 그 둘 다 지금 손에 없다.

반면 기획서(2)의 서비스들은 **외부 데이터 없이도 완성된다.** 교사의 시간표, 학급의 안건, 학생이 찍은 사진 — 사용자가 데이터를 만든다. 8월이라는 창을 낭비하지 않으려면 이쪽이 맞다.

### 실행계획(1)은 대기 상태다 (폐기 아님)

다만 **되돌아올 다리는 끊지 않는다.** 데이터 협조는 리드타임이 길어서, 8월에 요청을 걸어두지 않으면 12월까지 못 받는다.

| 조치 | 시점 | 비용 |
|---|---|---|
| D3 학교 위치 데이터 내려받아 `data/raw/`에 보관 | 8월 중 | 30분 (인증 불필요) |
| D2·D6·D8 협조 요청을 교육데이터 분과 경유로 발송 | 8월 중 | 공문 1건 |
| 대시보드 프로토타입 v0.1 현 상태 동결 | 지금 | 0 |

**복귀 조건: D2(학년별 학생·학급)가 확보되는 시점.** 그때 실행계획(1) 2주차부터 재개한다.

## 2. 기획서 10종 트리아지

기준은 네 가지다. ① 서버·DB·계정이 필요한가 ② 학생 개인 식별 정보를 다루는가 ③ 별도 콘텐츠 구축이 필요한가 ④ **다른 학교가 이미 참여해 있어야 가치가 생기는가**.

| # | 서비스 | 판정 | 사유 |
|---|---|---|---|
| ⑥ | 순회교사 스케줄러 | **채택 (A)** | 데이터 0, 개인정보 0, 만든 사람이 곧 사용자 |
| ④ | 공동체 소통·학급 회의 | **채택 (B)** | ⑦과 통합. 무기명 운영 시 개인정보 없음 |
| ⑦ | 학급 자율 의사결정 캘린더 | **채택 (B에 통합)** | ④와 기능 70% 중복. 따로 만들 이유 없음 |
| ⑤ | 지역 탐방 스토리북 | **채택 (C, 축소)** | GPS 미션맵은 제외. **에디터만** 제작 |
| ② | 성장 포트폴리오 | **보류** | 개인정보 정면. 로컬 저장 한정으로 축소 시 재검토 |
| ① | 학교 간 프로젝트 매칭 | 〔8/3〕 **축소 채택 (E)** | 매칭을 서버에 맡기지 않으면 오늘 된다. 아래 설명 |
| ③ | 마을-학교 잇기 | **제외** | 지역 자원 조사가 선행 과제. 8월 내 불가 |
| ⑧ | 교구 공동 대여소 | **제외** | 서버 필수. 단일 학교로 축소하면 가치 소멸 |
| ⑩ | 버추얼 동아리·페스티벌 | **제외** | 서버 + 참여 학교 필요 |
| ⑨ | AI 기초학력 배움터 | **제외** | 문항 DB 구축 + 학생 데이터. 규모가 다른 사업 |

### 제외 판정에 대한 설명

①③⑧⑩이 막히는 건 **기술이 아니라 구조** 때문이다. 매칭·공유·예약·전시는 상대방이 이미 들어와 있어야 동작한다. 8월에 완벽하게 만들어도 9월 시연에서 보여줄 게 "아무도 없는 게시판"이다. 이 셋(③⑧⑩)은 **데이터 플랫폼이 살아난 뒤** 그 위에 얹는 게 순서다.

### 〔8/3〕 ①은 「제외」에서 「축소 채택」으로 옮긴다 — 앱 E

위 판단은 **매칭을 서버가 한다고 볼 때** 옳다. 그런데 ①이 실제로 해결하려던 문제(작은 학교는 혼자 못 하는 일이 있다)를 놓고 보면, **혼자서도 되는 부분**이 남는다.

| | 기획서 ① 원안 | 앱 E |
|---|---|---|
| 학교 목록 | 받아야 함 | **앱 안에 있음** (경북 917교, 공공데이터) |
| 상대 학교 | 가입해 있어야 함 | **필요 없음** |
| 매칭 | 서버가 함 | **거리로 사람이 고름** |
| 결과물 | 게시판 | **종이 한 장** (제안서) |

찾기·계산·제안서는 상대가 없어도 오늘 된다. **연결은 사람이 전화로 한다.** 학교를 실제로 움직이는 것은 앱이 아니라 전화와 공문이기 때문이다.

앱 A가 학교 좌표를 얻고 나서야 되살아난 것과 같다. **제외 판정 당시와 조건이 달라졌다.**

②와 ⑨는 학생 개인정보를 다룬다. 〔8/3〕 ②(포트폴리오)는 여전히 **보류**다. 실행계획(1) R4의 "학교 단위 집계만, 학생 개인 데이터 미사용 원칙"과 충돌하고, 개인정보 영향평가 없이 교사 동아리 산출물로 배포할 수 없다.

**원안 기술 스택은 채택하지 않는다.** 기획서(2)는 React Native / Vue+Django / Next.js+Socket.io를 각각 제시하지만, 세 스택 모두 서버·빌드·배포 파이프라인을 요구한다. 4주 안에 완주할 수 없고, 12월 웹앱스토어 등록 시 보안성 검토도 통과하기 어렵다. 4장의 원칙으로 대체한다.

## 3. 왜 이 앱들인가

### A. 순회교사 통합 스케줄러 — 주제 정합성이 가장 높다

학령인구 감소 → 소규모학교 증가 → **순회·겸임 교사 증가**. 인과가 직선이다. "학령인구 감소 대응"이라는 연구소 주제에 설명이 필요 없는 유일한 앱이다.

그리고 이것만 **8월에 검증할 수 있다.** B는 학급이 있어야, C는 체험학습이 있어야 검증되지만, A는 만든 사람이 9월 1일부터 바로 사용자가 된다.

### B. 학급 자율 의사결정 보드 — 소규모 학급 특화 논리가 있다

기획서 ④·⑦은 사실상 같은 앱이다. 안건함·투표·약속 실천 체크가 겹친다.

핵심은 이것이다. **소규모 학급은 인원이 적어서 익명이 성립하지 않는다.** 6명 학급에서 손을 들면 누가 무슨 의견인지 다 보인다. 그래서 오히려 디지털 무기명 도구가 대규모 학급보다 절실하다. 이 논리가 "학령인구 감소 대응"과 앱을 연결한다.

### 〔8/3〕 D. 복식학급 수업 도우미 — 인과가 직선이다

학령인구 감소 → 소규모학교 증가 → **복식학급 증가.** 계획에 없었지만 기획서 10종이 소진된 자리에서 이 앱이 섰다. 복식학급 담임은 경북 소규모학교에 흔하고, 지금도 종이에 손으로 짠다.

### 〔8/3〕 E. 이웃 학교 함께하기 — 작은 학교가 혼자 못 하는 일

열두 명으로는 버스를 못 채우고, 한 학년 여덟 명으로는 반 대항 경기가 안 서고, 그 교과 교사가 한 명뿐이면 수업 이야기를 나눌 상대가 없다. 해답은 「가까운 학교와 함께」인데 **어느 학교가 가까운지를 교사가 모른다.** 아는 것은 같은 시군뿐이다.

안동 길안초에서 두 번째로 가까운 초등학교는 **의성군** 옥전초(10.4km)다. 같은 안동인 길주초(16.5km)보다 가깝다. **행정 구역이 아니라 거리가 이웃을 정한다.**

### C. 지역 탐방 디지털 스토리북 — 눈에 보이는 결과물이 남는다

원안의 GPS 미션맵·지역 역사 콘텐츠 구축은 뺀다. 콘텐츠는 우리가 만드는 게 아니라 **학생이 채우는 것**이다. 우리는 편집기와 인쇄 출력만 만든다.

12월 성과 발표회에 실물로 들고 갈 수 있는 산출물이 이것뿐이다. A와 B는 화면 캡처지만, C는 학생이 만든 책이 나온다.

## 4. 기술 원칙 (모든 앱 공통)

| 원칙 | 내용 | 이유 |
|---|---|---|
| **서버 없음** | 단일 HTML 파일. 백엔드·DB·계정 없음 | 4주 완주. 교육청 인프라 승인 절차 회피 |
| **로컬 저장** | `localStorage` + 파일 내보내기/가져오기(JSON) | 개인정보가 기기 밖으로 나가지 않음 |
| **외부 의존 0** | CDN·외부 폰트·외부 API 미사용 | 보안성 검토 유리. 오프라인 동작 |
| **이름 미사용** | 학생 실명 입력란을 만들지 않음 (번호·모둠명) | 개인정보 영향평가 회피 |
| **인쇄 지원** | 모든 앱에 인쇄용 CSS | 학교 현장은 여전히 종이로 결재·게시 |
| **접근성** | 대비 4.5:1, 키보드 전 조작, 색상 단독 정보전달 금지 | 12월 웹앱스토어 등록 대비 |

**LEAP Kit (공통 셸)을 먼저 만든다.** 모든 앱이 같은 CSS 토큰, 같은 저장 래퍼, 같은 내보내기/가져오기, 같은 접근성 기본값을 공유한다.

- 각자 만들면 10명이 만든 10개가 서로 다른 물건이 된다. 스토어에 올릴 때 제품군으로 안 보인다.
- 2번째·3번째 앱의 제작 속도가 눈에 띄게 빨라진다.
- 접근성·인쇄를 한 번만 제대로 잡으면 전 앱에 적용된다.

〔8/3〕 실제로 만들어진 모양은 이렇다. 폴더 이름은 `apps/` 로 갔다.

```
apps/
├─ index.html       ← 앱 카탈로그 (과제④ 웹앱스토어의 씨앗)
├─ test.js          ← 카탈로그 점검 (링크·판 번호·광고한 원칙이 사실인지)
├─ kit/
│  ├─ leap.css      ← 색·타이포·컴포넌트 토큰, 인쇄 스타일
│  └─ leap.js       ← 저장/불러오기, 내보내기/가져오기, 접근성 헬퍼
├─ a-circuit/       ← 앱 A  index.html · test.js · README.md
├─ b-classboard/    ← 앱 B
├─ c-storybook/     ← 앱 C  (+ test-epub.js)
├─ d-multigrade/    ← 앱 D
└─ e-together/      ← 앱 E
```

**앱마다 `test.js` 와 `README.md` 를 둔다.** 검사는 기능이 아니라 **그 앱이 약속한 규칙**을 지킨다(예: *"수집 중에는 안건 내용이 HTML에 없어야 한다"*, *"좌표를 모르는 학교가 거리 목록에 있으면 안 된다"*). README에는 **뺀 기능의 사유**까지 적는다. 전부 합쳐 718개다.

**공공데이터는 굽는다.** 경북 학교 917곳(위경도 포함)을 앱 A·C·E 파일 안에 심어 두었다. 앱을 열 때 인터넷을 부르지 않는다. 굽는 일은 만드는 사람이 `open api/bake-coords.mjs` 로 한 번 하고, **인증키는 배포물에 들어가지 않는다.**

## 5. 앱별 제작 범위

### A. 순회교사 통합 스케줄러

**해결하는 문제**: 순회·겸임 교사는 학교 2~4곳의 서로 다른 학사일정·시간표·업무를 한 화면에서 못 본다. 종이 수첩과 각 학교 나이스를 오간다.

| 구분 | 범위 |
|---|---|
| **핵심 기능** | ① 담당 학교 다중 등록 ② 주간 통합 시간표 (학교별 색 + 라벨) ③ 이동 시간 충돌 경고 ④ 학교별 진도·특이사항 일지 ⑤ 학사일정 겹침 표시 〔8/3〕 **v0.2로 미룸** ⑥ 주간 인쇄 |
| **제외** | 나이스 연동, 실시간 동기화, 학부모 공유 |
| **데이터** | `schools[]`, `periods[]`, `lessons[]`, `notes[]` — 전부 로컬 |
| **개인정보** | 없음. 학급 단위까지만 (예: "3-1"), 학생 이름 없음 |
| **검증** | 9월 개학 직후 제작자 본인 실사용 4주 |

가장 중요한 기능은 **③ 이동 시간 충돌 경고**다. 다른 도구에 없고, 순회 교사가 실제로 겪는 사고(학교 간 이동 시간 부족)를 막는다. 이게 이 앱의 존재 이유다.

> 〔8/3〕 이 기능 때문에 8월 초에는 A를 뺐다. **학교 좌표가 없어서** 이동 시간을 말할 수 없었기 때문이다. 앱 C를 위해 경북 917교의 위경도를 구우면서 조건이 달라졌고, 되살렸다. 지금은 **분 단위 실제 시각**으로 겹침을 보고(교시 번호가 아니라), 이미 찬 시각의 교시는 **눌리지 않는다.**

### B. 학급 자율 의사결정 보드

**해결하는 문제**: 소규모 학급에서는 익명이 성립하지 않아 솔직한 의견이 나오지 않는다.

| 구분 | 범위 |
|---|---|
| **핵심 기능** | ① 무기명 안건 제출 ② 안건 투표 (찬반/선택형) ③ 결정 사항 기록 ④ 학급 약속 실천 체크리스트 ⑤ 회의록 인쇄 |
| **제외** | 감정 체크인(개인 심리 데이터), 가정 연계 알림, 계정 |
| **운영 방식** | 교실 기기 1대를 순회하거나, 각자 기기에서 같은 파일을 열고 결과를 합침 |
| **데이터** | `agendas[]`, `votes[]`, `rules[]` — 이름 필드 없음 |
| **검증** | 9월 개학 후 학급 적용 (담임 참여자 필수) |

**무기명 보장 설계에 주의한다.** 소규모 학급에서는 제출 순서만으로도 누가 썼는지 추정 가능하다. 저장 시 순서를 섞고, 제출 시각을 기록하지 않는다.

### C. 지역 탐방 디지털 스토리북

**해결하는 문제**: 체험학습 결과물이 사진 폴더로만 남고 정리되지 않는다.

| 구분 | 범위 |
|---|---|
| **핵심 기능** | ① 페이지 편집 (사진 + 글) ② 표지 템플릿 ③ 자동 레이아웃 ④ 인쇄용 출력 ⑤ 파일 내보내기로 공유 |
| **제외** | GPS 미션맵, 지역 역사 콘텐츠 DB, 음성 녹음(1차), 온라인 출판 |
| **데이터** | `book{ title, pages[{ image, text }] }` — 이미지는 Base64로 파일 내부 |
| **개인정보** | 사진에 학생 얼굴이 들어갈 수 있음 → **파일이 기기 밖으로 나가지 않음을 화면에 명시**, 공유 시 교사 판단 |
| **검증** | 10월 체험학습 활용 |

〔8/3〕 실제로는 계획보다 넓어졌다 — EPUB 내보내기, 여러 권을 담는 책장(IndexedDB), 합본, 경북 22개 시군 탐방 지도, 학교 이름으로 우리 학교 찾기.

### 〔8/3〕 D. 복식학급 수업 도우미

**해결하는 문제**: 두 학년을 한 교실에서 가르치는 한 차시를 짜기 어렵다. 지금은 종이에 손으로 짠다.

| 구분 | 범위 |
|---|---|
| **핵심 기능** | ① 8구간 시간 배치 ② 활동·준비물 ③ 학년별 학습지 ④ 점검(치우침·혼자 있는 시간·할 거리 없음) ⑤ 지도안 미리보기·인쇄 ⑥ AI 초안 프롬프트 |
| **제외** | 3개 학년 복식, API 키를 넣는 AI 호출 |
| **지키는 규칙** | **교사는 한 시점에 한 학년만 직접지도할 수 있다** → 성립 가능한 배치 4가지 중에서만 고르게 해서, 어길 방법 자체를 없앰 |
| **개인정보** | 없음. 학년까지만 |
| **검증** | 9월 복식학급 담임이 한 차시를 짜 보기 |

### 〔8/3〕 E. 이웃 학교 함께하기

**해결하는 문제**: 작은 학교는 혼자서 버스를 못 채우고 연합 행사를 못 연다. 함께 할 학교를 찾는 일이 지금은 「아는 사람에게 전화」로만 이뤄진다.

| 구분 | 범위 |
|---|---|
| **핵심 기능** | ① 우리 학교·인원·목적 ② **가까운 순 이웃 목록(시군 경계를 넘어서)** + 반경 지도 ③ 버스 나눠 타기 계산 · 경유 시간 · 모이는 자리 ④ **제안서 인쇄**(전화로 물어볼 것 포함) |
| **제외** | 서버 매칭, 게시판, 상대 학교 계정 — 연결은 **사람이 전화로** 한다 |
| **지키는 규칙** | 좌표를 모르는 학교는 거리 순위에 섞지 않는다 · **「함께가 항상 이득」이라고 말하지 않는다**(1인당 부담이 느는 학교를 그대로 적는다) · 거리는 「직선」이라 적는다 · 상대 학교 인원을 추측하지 않는다 |
| **개인정보** | 없음. 인원 **수**만 |
| **검증** | 10월 체험학습 — 제안서를 들고 실제로 전화 걸어 보기 |
