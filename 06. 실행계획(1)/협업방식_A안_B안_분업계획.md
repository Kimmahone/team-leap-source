## 0. A·B 어느 쪽이든 바뀌지 않는 것

분업 계획을 읽기 전에 이 여섯 가지는 공통 전제입니다.

### ① 저장소가 두 개입니다

| 저장소 | 정체 | 사람이 만지나 |
|---|---|---|
| `team-leap-source` | **원본.** 코드·문서가 여기 있습니다 | ✅ 여기서만 작업 |
| `team-leap` | **결과물.** 구운 사이트가 자동으로 밀려 올라갑니다 | ❌ 손대지 않음 |

설정도, 초대도, PR도 전부 **`team-leap-source`** 에서 합니다.

### ② `main` = 라이브입니다 (스테이징이 없습니다)

```
main 에 들어감
  └→ 사이트 굽기(검사 포함) → team-leap → Cloudflare Pages → 공개 사이트
```

머지하는 순간 공개 사이트가 바뀝니다. **되돌리는 길은 `git revert` 뒤 push** 이고,
그 push 자체가 재배포입니다.

### ③ 대시보드가 «파일 하나»입니다

`06. 실행계획(1)/prototype/index.html` — **4,600줄 / 약 500KB.**
CSS·마크업·JS가 한 파일에 다 들어 있습니다. 빌드 도구도 번들러도 없습니다.

이것이 인원과 분업을 정하는 **가장 큰 제약**입니다.

### ④ 파일 안에 «구역»을 나눠 두었습니다

```
CSS 디자인팀 구역     </style> 바로 위          ← 디자인팀 전용
JS  기능팀 구역       「8. 초기화」 바로 위      ← 기능팀 전용
마크업 기능팀 자리     홈 화면 좌·우 두 곳       ← 기능팀 전용
데이터 줄             1,750~1,800 / 3,200~3,230 ← 아무도 손대지 않음(봇 전용)
```

같은 파일이라도 **서로 다른 줄**을 고치면 Git은 조용히 합쳐 줍니다.
구역을 지키는 것이 곧 충돌을 피하는 방법입니다.

### ⑤ 보이지 않는 네 번째 작업자 — 자동 갱신 봇

| 갱신 | 주기 | 무엇을 |
|---|---|---|
| 주간 뉴스 | 매주 월요일 아침 | `news-history.json`, `index.html` |
| KOSIS 개정 | 매월 | `index.html` 데이터 줄 |
| 학교·유치원·좌표 | 분기 | `index.html` 데이터 줄 |
| 교육통계(EDSS) | 매년 9월 | `index.html` 데이터 줄 |

봇은 `main` 에 **직접 커밋·푸시**합니다.
그래서 **브랜치를 오래 들고 있을수록 충돌합니다.** 3~5일이 한계선입니다.

### ⑥ 이미 갖춰 둔 준비물

## 1. A안 — 무료, 「약속」으로 운영

### 1-1. 무엇이 되고 무엇이 안 되나

**됩니다**: 브랜치, PR, 리뷰, 의견, **PR 검사 자동 실행(✅/❌ 표시)**, PR 서식, 되돌리기

**안 됩니다** (막아 주는 장치가 없음):

| 상황 | A안에서 |
|---|---|
| 브랜치 없이 `main` 에 바로 push | **그냥 됩니다** → 그 순간 라이브 갱신 |
| 검사가 ❌인데 Merge 누름 | **눌립니다** |
| 리뷰 없이 혼자 Merge | 됩니다 |
| force push (이력 날림) | 됩니다 |

> **가장 위험한 시나리오**
> 팀원이 브랜치를 잊고 `main` 에 바로 push → 라이브가 즉시 바뀜 →
> 검사는 그 **뒤에** 돌고 실패 → 사이트는 낡은 채 남고, 아무도 모릅니다.

### 1-2. 분업 계획

#### 역할 셋

**① 통합·검토자 — 김선생님**

| 항목 | 내용 |
|---|---|
| 만지는 곳 | `main` 전체, 데이터 도구(`open api/`), 자동화(`.github/`), 굽기 스크립트, 운영문서 |
| 하는 일 | PR 검토·머지 · 배포 결과 확인 · 데이터 갱신 관리 · 충돌 조정 |
| **A안에서 추가로** | **주 1회 이력 점검** — 브랜치 없이 들어온 커밋이 없는지 확인 |
| 하지 않는 일 | 두 팀의 구역을 대신 고치기 (충돌의 원인이 됩니다) |

**② 디자인팀 — 1명 권장**

| 항목 | 내용 |
|---|---|
| 브랜치 | `design/무엇을-바꾸는지` |
| 만지는 곳 | `:root` 의 `--leap-*` 토큰 **(네 벌 모두)** · `</style>` 위 「디자인팀 구역」 |
| 하지 않는 일 | 마크업, JS, 데이터 줄, **파일 전체 포매터** |
| 반드시 확인 | 밝은 화면 · **어두운 화면** · 인쇄 미리보기 · 좁은 화면(720px) · 지도 크게 보기 · 메뉴 접기 |
| 함정 | 토큰이 **한 파일에 네 벌**, 저장소 전체로는 **열일곱 벌**입니다 |
| 읽을 문서 | `00. 운영문서/08_디자인팀_색과_치수.md` |

**③ 기능 추가팀 — 1명 권장**

| 항목 | 내용 |
|---|---|
| 브랜치 | `feat/무엇을-더하는지` |
| 만지는 곳 | 마크업 「기능팀 자리」(홈 좌·우) · 「기능팀 구역」(JS) · `test.js` 에 검사 추가 |
| 하지 않는 일 | 기존 CSS 규칙, 데이터 줄, 외부 주소 호출(검사가 막습니다) |
| 산출 순서 | ⓵ **빈 골격만 먼저 작게 머지** → ⓶ 내용 채우기 |
| 반드시 확인 | `node test.js` 전부 OK · 다크 모드 · 인쇄 |

> **왜 「빈 골격 먼저」인가** — 디자인팀이 스타일을 입힐 «자리»가 먼저 있어야 합니다.
> 순서를 뒤집으면 디자인 작업을 두 번 하게 됩니다.

#### 주간 흐름

```
월요일   김선생님: 지난주 머지분이 라이브에 나갔는지 확인 (봇 뉴스 갱신도 이날)
         전원:     git pull --rebase origin main
화~목    각자 브랜치에서 작업 · 매일 아침 rebase 한 번
         작은 단위로 PR 을 올림 (크면 쪼갬)
금요일   PR 정리·머지
         ※ 금요일 «늦은» 머지는 피합니다 — 머지가 곧 배포이고,
            문제가 생기면 주말에 아무도 못 봅니다
```

#### A안을 지탱하는 「약속」 다섯 줄

1. `main` 에 **직접 push 하지 않는다.** 반드시 브랜치 → PR.
2. PR 검사가 **✅ 일 때만 Merge** 한다.
3. 브랜치는 **3~5일 안에** 정리한다.
4. **내 구역 밖을 건드리지 않는다.**
5. **포매터를 돌리지 않는다.**

### 1-3. 위험과 대비

| 위험 | 대비 |
|---|---|
| 실수로 `main` 직접 push | **감시 워크플로**를 붙일 수 있습니다 — 막지는 못해도 Actions에 눈에 띄게 경고가 남습니다 |
| ❌인 채로 머지 | 김선생님이 머지 담당을 맡고, 팀은 PR만 올리는 방식으로 좁힙니다 |
| 라이브가 깨짐 | `git revert` 후 push. **되돌리는 편이 고쳐 올리는 것보다 항상 빠릅니다** |
| force push 로 이력 손실 | 김선생님이 주 1회 `git log --first-parent` 로 확인 |

### 1-4. 이 안이 맞는 경우

- 동시 작업자가 **3명 이하**이고 서로 말이 통하는 사이
- 사이트가 잠깐 낡아도 큰일이 아닌 시기
- 비용을 들이기 전에 **한두 달 굴려 보고 판단**하고 싶을 때

## 4. 몇 명이 적당한가

**핵심 제약은 사람 수가 아니라 「파일이 하나」라는 점**입니다.
Git은 **같은 줄**을 두 사람이 고칠 때만 충돌합니다. 그래서 구역을 나눠 둔 것이고,
**구역이 3개이므로 동시에 브랜치를 열고 있는 사람은 2~3명이 설계 한계**입니다.

| 동시 작업자 | 상태 |
|---|---|
| 2명 (디자인 1 + 기능 1) | 여유 있음. 구역이 안 겹칩니다 |
| **3명** (+ 김선생님) | ✅ **현재 계획. 딱 맞습니다** |
| 4~5명 | 구역이 겹치기 시작. 매일 rebase 필수, 충돌 잦아짐 (B안 권장) |
| 6명 이상 | **파일을 먼저 쪼개야 합니다** — `theme.css` / `app.js` 분리 + 굽기 스크립트에 복사 한 줄 추가 |

> **인원수보다 중요한 것**: 브랜치를 3~5일 안에 정리하는 것.
> 2주 묵힌 브랜치 하나가 4명이 동시에 작업하는 것보다 아픕니다.
> 봇이 같은 파일을 매주·매월 고치기 때문입니다.

## 6. 언제 A에서 B로 옮기나 — 신호 넷

- [ ] 검사가 ❌인데 머지된 일이 **한 번이라도** 생겼을 때
- [ ] 브랜치 없이 `main` 에 직접 push 된 일이 생겼을 때
- [ ] 동시 작업자가 **4명을 넘을 때**
- [ ] 대외 공개·보고가 가까워졌을 때

옮기는 데 드는 일은 **2-3절의 여섯 단계, 20분 남짓**입니다. 언제든 늦지 않습니다.

---

## 7. 정하기 전에 답해야 할 질문

- [ ] 두 팀을 **내 저장소에 초대**할 것인가, 다른 방식으로 받을 것인가
- [ ] 초대한다면 — 전원이 쓰기 권한을 갖는 것을 감수할 수 있는가 (5절)
- [ ] 두 팀의 **GitHub 아이디**를 받을 수 있는가
- [ ] 두 팀이 **Git·PR 사용 경험**이 있는가 (없다면 A안 + 김선생님 머지 담당이 안전)
- [ ] 저장소에 든 **내부 계획서·공문 초안**을 외부 팀이 보아도 되는가
- [ ] 사이트가 **하루 낡아 있어도** 괜찮은가 (아니라면 B안)

## 부록: 다른 협업 방식을 택할 경우

이 문서는 **「내 저장소에서 함께 작업한다」** 는 가정 위에 있습니다. 다른 길도 있습니다.

| 방식 | 특징 | 이 문서에서 살아남는 부분 |
|---|---|---|
| **파일을 주고받는다** | 가장 쉬움. 대신 합치는 일을 김선생님이 손으로 함. 두 팀이 동시에 고치면 한쪽을 버려야 함 | 「구역 나누기」와 「확인 항목」만 유효 |
| **포크(fork) 후 PR** | 초대 없이 받을 수 있음. 외부 팀이 저장소를 만지지 못함. 대신 PR 검사가 외부 포크에서는 제한될 수 있음 | 대부분 유효 |
| **조직으로 옮긴다** | 권한을 나눌 수 있음. 저장소 주소가 바뀌므로 배포 설정(`deploy.sh`, Cloudflare 연결)을 함께 손봐야 함 | 전부 유효 + 5절 해결 |
| **디자인만 따로 받는다** | 디자인팀은 시안(Figma·이미지)만 주고, 코드는 김선생님이 반영. 충돌이 원천적으로 없음 | 「디자인팀 안내」 문서가 시안 기준이 됨 |

> 두 팀 중 **디자인팀만 시안으로 받고, 기능팀만 저장소에 초대하는** 절충도 가능합니다.
> 이 경우 동시 작업자가 2명이 되어 A안으로 충분해집니다.
