# TEAM LEAP 데이터 보관과 프로젝트 인수인계

작성일: 2026-09-11  
대상: 경북 학령인구 데이터 플랫폼 원본 저장소와 배포 저장소  
목적: 담당자가 바뀌어도 데이터, 자동화, API 연결, 배포 구조를 안전하게 재현하기 위한 최종 인수인계 기준

## 1. 먼저 알아야 할 결론

1. 현재 서비스에는 운영 중인 데이터베이스가 없다.
2. 뉴스와 이슈페이퍼 히스토리는 JSON 파일로 저장되고, Git 커밋이 변경 이력이 된다.
3. 화면에 보이는 2016~2025 EDSS 집계와 2026 학교 자료 중 상당수는 `prototype/index.html` 안에 구워져 있다.
4. 빅카인즈 원본과 대용량 참고자료는 공개 GitHub에 올리지 않고 제한된 공유 폴더로 넘긴다.
5. API 키 값은 넘기지 않는다. 후임자가 자신의 키를 발급받아 GitHub와 Cloudflare에 다시 등록한다.
6. 기존 저장소를 소유자 계정에 남길 예정이므로, 인계 방식은 포크보다 **독립 저장소 복제**가 적합하다.
7. 현재 보존된 자료는 모두 인계할 수 있지만, 과거 API 원본 응답 전체가 남아 있는 것은 아니다. 원본이 없는 자료는 가공본과 재수집 코드로 인계한다.

## 2. 현재 시스템 구조

```text
공공 API·네이버 뉴스 API·빅카인즈 원본
                 │
                 ▼
       수집·정제·검사 프로그램
                 │
        ┌────────┴────────┐
        ▼                 ▼
원본 저장소              제한 공유 폴더
team-leap-source         빅카인즈·통계 원자료
JSON/CSV/코드/문서        PDF/XLSX/HWP 등
        │
        │ GitHub Actions에서 검사·굽기
        ▼
배포 저장소 team-leap
        │
        ▼
Cloudflare Pages 공개 서비스
```

`backend/`는 향후 Cloudflare D1·R2 도입을 위한 설계와 스키마만 갖춘 상태다. D1 데이터베이스와 R2 버킷은 아직 만들지 않았으므로, 현재 운영 방식은 **정적 파일 + Git 버전 관리 + Pages Functions**다.

## 3. 뉴스와 이슈페이퍼는 어디에 저장되는가

### 3.1 최신 뉴스

| 항목 | 현재 방식 |
|---|---|
| 저장 파일 | 저장소 루트의 `news-history.json` |
| 수집 출처 | 네이버 뉴스 검색 API |
| 자동 수집 | 매일 오전 7시 37분, GitHub Actions |
| 보관 범위 | 최근 120일 |
| 현재 확인 수량 | 177건, 2026-09-11 확인 |
| 변경 이력 | Git 커밋으로 남음 |
| 데이터베이스 | 사용하지 않음 |

관련 파일:

- 자동화: `.github/workflows/update-news.yml`
- 수집 프로그램: `fetch-news.js`
- 보관 기간: `fetch-news.js`의 `HISTORY_DAYS = 120`

따라서 뉴스는 무한정 쌓이지 않는다. 매일 새 기사를 추가하되 120일보다 오래된 항목은 현재 JSON에서 내려간다. 과거 커밋에는 흔적이 남지만, Git 기록을 장기 뉴스 저장소처럼 사용하는 것은 권장하지 않는다.

### 3.2 주간 이슈페이퍼

| 항목 | 현재 방식 |
|---|---|
| 저장 파일 | `06. 실행계획(1)/prototype/assets/news/issues/index.json` |
| 생성 주기 | 매주 일요일 오전, 같은 뉴스 자동화 안에서 생성 |
| 수동 생성 | GitHub Actions의 `workflow_dispatch` 또는 로컬 명령 |
| 보관 한도 | 최신순 최대 52호 |
| 현재 확인 수량 | 2호, 2026-09-11 확인 |
| PDF 보관 | 자동 보관하지 않음 |

화면의 이슈페이퍼는 JSON을 기사형 화면으로 렌더링한다. 사용자가 `인쇄 · PDF 저장`을 눌러 만든 PDF는 사용자의 컴퓨터에만 저장되며 저장소나 서버에는 자동 업로드되지 않는다.

### 3.3 빅카인즈 장기 분석

빅카인즈는 자동 크롤링 API가 아니라 내려받은 엑셀 원본을 분석한다.

| 구분 | 위치 | 공개 여부 |
|---|---|---:|
| 2016~2026 연도별 원본 11개 | 로컬 `뉴스 크롤링/빅카인즈/` | 비공개 인계 |
| 원본 체크섬·행 수 | `news-pipeline/source-manifest.json` | 저장소 포함 |
| 공개 분석 요약 | `prototype/assets/news/manifest.json` | 공개 가능 |
| 화면용 스냅샷 | `prototype/assets/news/snapshot.json` | 공개 가능 |
| 키워드 연결망 | `prototype/assets/news/network.json` | 공개 가능 |
| 중간 분석자료 | `news-pipeline/work/` 또는 로컬 `뉴스 크롤링/output/` | 비공개 인계 |

2026-09-10 생성본 기준:

- 원본 29,277행
- 중복 제거 후 19,980행
- 학령인구 관련 6대 주제로 선별한 기사 8,633행
- 시각화·유사도 분석에 사용한 기사 1,875행
- 분석 기간 2016-01-04~2026-09-09

기사 본문이나 전체 기사 목록은 저작권과 이용조건을 고려해 공개 GitHub에 올리지 않는다. 원본은 교육청 또는 팀의 제한된 공유 폴더에서 담당자에게만 권한을 부여한다.

### 4.3 현재 남아 있지 않은 원본

다음 자료는 화면용 가공 결과나 재수집 코드만 있고, 과거 API 응답 원문 전체는 보존하지 않았다.

- EDSS 약 97,134행의 학교별 원본 응답 전체
- 학교알리미 2026 원본 API 응답 전체
- 유치원알리미 원본 API 응답 전체
- SGIS 지도 요청의 원본 응답
- Gemini AI 인사이트 요청·응답
- 네이버 API가 반환한 모든 검색 응답 원문

이것은 자료 유실이라기보다 현재 정적 앱의 설계 방식이다. 다만 다음 운영 단계부터는 API 응답 원본을 날짜별로 R2 또는 제한 저장소에 보존하는 편이 좋다.

## 5. API 키는 어떻게 인계하는가

### 5.1 원칙

- 기존 담당자의 키 값은 문서, 메신저, 압축파일, Git에 넣지 않는다.
- 후임자가 각 기관에서 자신의 키를 발급받는다.
- 문서에는 환경변수 이름, 발급처, 등록 위치, 점검 방법만 남긴다.
- 인계 완료 후 기존 담당자의 키는 필요에 따라 허용 도메인·권한을 줄이거나 폐기한다.

### 5.2 GitHub Actions에 등록할 항목

새 원본 저장소의 `Settings → Secrets and variables → Actions`에 등록한다.

| 이름 | 용도 |
|---|---|
| `DEPLOY_PAT` | 새 배포 저장소에 자동 푸시 |
| `NAVER_CLIENT_ID` | 최신 뉴스 수집 |
| `NAVER_CLIENT_SECRET` | 최신 뉴스 수집 |
| `SCHOOLINFO_API_KEY` | 학교알리미 갱신 |
| `KOSIS_API_KEY` | KOSIS 갱신 |
| `KINDER_API_KEY` | 유치원알리미 갱신 |
| `EDSS_SCHOOL_ATTRIBUTE_API_KEY` | EDSS 학교속성 |
| `EDSS_CLASS_STUDENT_API_KEY` | EDSS 학급·학생 현황 |
| `EDSS_STUDENT_STATUS_API_KEY` | EDSS 유초중등학생현황 |
| `EDSS_CLASS_STATUS_API_KEY` | EDSS 유초중등학급현황 |
| `EDSS_SCHOOL_LOCATION_API_KEY` | EDSS 학교 위치 |
| `EDSS_SCHOOL_OVERVIEW_API_KEY` | EDSS 학교 개황 |
| `EDSS_EDU_STAT_SCHOOL_OVERVIEW_API_KEY` | EDSS 교육통계 학교 개황 |

GitHub Actions 변수에는 `PUBLIC_DATA_YEAR=2026`을 등록한다. 새 공시연도로 전환할 때 이 값을 바꾼다.

### 5.3 Cloudflare Pages에 등록할 항목

새 Cloudflare Pages 프로젝트의 `Settings → Variables and Secrets`에서 Preview와 Production 환경을 각각 확인한다.

| 이름 | 용도 |
|---|---|
| `GEMINI_API_KEY` | 학생수 시뮬레이터 AI 인사이트 |
| `SGIS_CONSUMER_KEY` | 실제 위치 지도 |
| `SGIS_CONSUMER_SECRET` | SGIS 호환용 보조 키, 필요한 경우 |
| `VWORLD_API_KEY` | 기존 브이월드 진단 기능을 유지할 경우 |

지도 API에서 허용 도메인을 제한했다면 새 Cloudflare 도메인과 커스텀 도메인을 다시 등록한다.

### 5.4 로컬 개발

후임자는 저장소의 `.dev.vars.example`을 복사해 `.dev.vars`를 만들고 자신의 키만 입력한다. `.dev.vars`, `.env`, `open api/인증키.txt`는 `.gitignore` 대상이므로 커밋하지 않는다.

## 6. 포크, 이전, 독립 복제 중 무엇을 선택할까

| 방식 | 장점 | 단점 | 이 프로젝트 적합성 |
|---|---|---|---|
| 포크 | 원본과 연결된 채 수정 제안·PR을 보내기 쉬움 | 비공개 포크는 원본 권한과 네트워크에 종속됨 | 공동 개발에는 가능, 최종 인계에는 비권장 |
| 저장소 소유권 이전 | 이슈·PR·설정 등 GitHub 맥락을 가장 많이 보존 | 기존 소유자가 완전히 넘겨야 함 | 원본을 내 계정에 남기려는 현재 목적과 다름 |
| 독립 저장소 복제 | 내 원본을 그대로 두고 새 조직이 독립 운영 | Secrets·Cloudflare·PR/Issue는 별도 이전 필요 | **권장** |

후임자가 잠시 개발에 참여하고 원본 저장소로 PR을 보낼 목적이면 포크도 괜찮다. 그러나 운영 주체 자체를 넘기면서 기존 저장소는 내 계정에 보존하려면, 새 조직 소유의 빈 저장소를 만들고 Git 이력을 독립 복제하는 방식이 가장 깔끔하다.

## 7. 독립 저장소 복제 절차

### 7.1 새 운영 주체가 먼저 만들 것

개인 계정보다 교육청 또는 팀의 GitHub Organization을 권장한다.

1. 비공개 빈 저장소 `team-leap-source` 생성
2. 비공개 또는 공개 배포용 빈 저장소 `team-leap-site` 생성
3. 두 저장소를 만들 때 README, `.gitignore`, License를 자동 생성하지 않음
4. 운영 담당자에게 Admin, 개발 담당자에게 Write 권한 부여

### 7.2 원본 저장소 전체 이력 복제

아래의 `NEW_OWNER`는 새 조직 또는 후임자 계정명으로 바꾼다.

```bash
git clone --mirror https://github.com/Kimmahone/team-leap-source.git
cd team-leap-source.git
git push --mirror https://github.com/NEW_OWNER/team-leap-source.git
cd ..
```

### 7.3 배포 저장소 전체 이력 복제

```bash
git clone --mirror https://github.com/Kimmahone/team-leap.git
cd team-leap.git
git push --mirror https://github.com/NEW_OWNER/team-leap-site.git
cd ..
```

### 7.4 새 저장소를 평소 작업용으로 받기

```bash
git clone https://github.com/NEW_OWNER/team-leap-source.git
cd team-leap-source
git remote -v
```

### 7.5 코드 안에서 바꿀 항목

| 위치 | 바꿀 내용 |
|---|---|
| `.github/deploy.sh` | `Kimmahone/team-leap.git`을 새 배포 저장소 주소로 변경 |
| `.github/CODEOWNERS` | `@Kimmahone`을 새 책임자 또는 팀으로 변경 |
| README·운영문서 | 기존 소유자명, 저장소 URL, 서비스 URL 변경 |
| Cloudflare Pages | 새 배포 저장소 `team-leap-site` 연결 |
| API 제공기관 | 새 Pages 도메인을 허용 도메인에 등록 |

### 7.6 복제로 자동 이전되지 않는 것

- GitHub Actions Secrets와 Variables
- GitHub Collaborators·Teams·권한
- Branch protection·Rulesets
- GitHub Issues, Pull Requests, Discussions의 운영 맥락
- Cloudflare Pages 프로젝트·도메인·환경변수
- API 제공기관의 키와 허용 도메인

Git 커밋 이력, 브랜치, 태그는 `--mirror`로 복제되지만 위 항목은 새 계정에서 다시 설정해야 한다.

## 8. Cloudflare와 자동 배포 재연결

1. 새 Cloudflare Pages 프로젝트를 만든다.
2. 새 운영 주체의 `team-leap-site` 저장소를 연결한다.
3. Production branch를 `main`으로 설정한다.
4. Pages Functions가 포함되어 배포되는지 확인한다.
5. `GEMINI_API_KEY`, `SGIS_CONSUMER_KEY` 등 런타임 키를 등록한다.
6. 새 원본 저장소에 `DEPLOY_PAT`을 등록한다.
7. 원본 저장소의 `.github/deploy.sh` 대상 주소를 새 배포 저장소로 바꾼다.
8. 원본 저장소에서 수동 Actions 실행 후 배포 저장소에 커밋이 생기는지 확인한다.
9. 새 Pages 주소에서 지도, AI 인사이트, 뉴스, 인쇄 기능을 확인한다.

## 10. 후임자가 받자마자 할 일

1. 패키지의 `SHA256SUMS.txt`를 검사한다.
2. 새 GitHub 조직에 원본·배포 저장소 두 개를 독립 복제한다.
3. `CODEOWNERS`와 배포 대상 저장소 주소를 바꾼다.
4. 자신의 API 키를 발급하고 GitHub Actions Secrets에 등록한다.
5. 새 Cloudflare Pages 프로젝트를 배포 저장소와 연결한다.
6. Cloudflare 환경변수와 지도 허용 도메인을 설정한다.
7. `사이트 굽기.command`로 전체 검사를 수행한다.
8. 뉴스 자동화를 수동 실행해 수집→커밋→배포 흐름을 확인한다.
9. 공공데이터 갱신을 수동 실행해 실패 시 직전 정상본이 유지되는지 확인한다.
10. 담당자와 갱신 주기, 공개 승인, 장애 대응자를 운영문서에 기입한다.

## 12. 최종 인수 완료 기준

다음 항목이 모두 충족되어야 인계 완료로 본다.

- 새 담당자가 원본 저장소를 clone하고 전체 검사를 통과했다.
- 새 원본 저장소의 Actions가 새 배포 저장소를 갱신한다.
- 새 Cloudflare 주소에서 모든 핵심 화면이 열린다.
- 최신 뉴스가 수집되고 주간 이슈페이퍼가 생성된다.
- 실제 위치 지도와 AI 인사이트가 후임자 키로 작동한다.
- 2016~2025 EDSS 가공자료, 2026 공시자료, 뉴스 원본·가공자료를 모두 찾을 수 있다.
- 비공개 원자료가 공개 저장소에 포함되지 않았다.
- 기존 담당자의 키 값이 어떤 파일이나 Git 이력에도 들어가지 않았다.
- 데이터별 담당자, 갱신 주기, 공개 승인자, 장애 대응자가 정해졌다.
