# 공동작업 협업 규칙

작성: 2026-09-02

디자인팀과 기능 추가팀이 이 저장소에 함께 들어오면서 정한 규칙입니다.
**새로 합류한 팀은 이 문서를 먼저 읽습니다.**

---

## 1. 먼저 알아야 할 세 가지

### ① 대시보드는 파일 한 개입니다

```
06. 실행계획(1)/prototype/index.html      4,589줄 / 472KB
├─ 11~640줄     CSS  (<style> 한 덩어리)
├─ 642~1343줄   화면 마크업
└─ 1344~4586줄  JS   (<script> 한 덩어리)
```

빌드 도구도 번들러도 없습니다. 이 파일을 그대로 브라우저가 엽니다.
두 팀이 동시에 열면 충돌이 납니다. 그래서 **브랜치만이 아니라 파일 안의 구역도 나눕니다**(3절).

### ② `main`에 들어가면 곧바로 라이브입니다

```
main에 push
  └→ .github/workflows/update-news.yml  (on: push, branches:[main])
       └→ 사이트 굽기.command            (보안·링크·유닛 검사 포함)
            └→ .github/deploy.sh
                 └→ Kimmahone/team-leap 저장소
                      └→ Cloudflare Pages (운영 사이트)
```

스테이징 환경이 없습니다. `main` = 운영입니다.
검사에 걸리면 배포가 멈추고 **사이트는 직전 정상본을 유지**합니다(=새 작업이 반영되지 않은 채 조용히 남습니다).

### ③ 봇도 같은 파일을 고칩니다

`.github/workflows/refresh-core.yml`이 공공데이터를 구운 뒤
`06. 실행계획(1)/prototype/index.html`을 **직접 커밋하고 `main`에 push**합니다.

| 갱신 | 주기 |
|---|---|
| 주간 뉴스 클리핑 | 매주 월요일 아침 |
| KOSIS 개정 확인 | 매월 |
| 학교·유치원·좌표 | 분기 |
| 교육통계(EDSS) | 매년 9월 |

봇이 덮어쓰는 자리는 index.html 안의 **1700~1750줄, 3150~3179줄 부근**의 긴 데이터 문자열입니다.
브랜치를 오래 들고 있을수록 이 커밋과 충돌합니다.

---

## 2. 브랜치 규칙

```
main          운영. 직접 push 금지. PR로만 머지.
design/*      디자인팀   예) design/dashboard-theme
feat/*        기능 추가팀 예) feat/home-지표추가
fix/*         버그 수정
```

- **브랜치 수명은 3~5일.** 길어지면 봇 커밋과 충돌합니다. 크면 쪼갭니다.
- 매일 아침 한 번: `git pull --rebase origin main`
- 커밋 메시지는 기존 방식을 따릅니다: `feat:` `fix:` `docs:`
- PR은 작게. 리뷰어 1명. `node test.js` 통과 후 올립니다.

### ⚠️ 브랜치 보호를 켤 때 반드시 확인할 것

GitHub Settings에서 "Require a pull request before merging"을 켜면
**봇의 데이터 갱신 push가 함께 막힙니다.**

→ Settings → Rules(또는 Branch protection)에서 `github-actions[bot]`을
   **bypass 목록에 반드시 추가**합니다.

빠뜨리면 몇 주 뒤 "데이터가 왜 안 바뀌지" 상태가 됩니다.
Actions 화면에 실패가 남지만 아무도 보지 않게 되는 종류의 실패입니다.

## 3. 파일 안의 구역 나누기

파일이 하나이므로, 팀마다 **손대는 줄이 겹치지 않게** 미리 자리를 정합니다.

| 팀 | 손대는 곳 | 손대지 않는 곳 |
|---|---|---|
| **디자인팀** | `:root`의 `--leap-*` 토큰(색·간격·글꼴·그림자)<br>`</style>` 직전 **「디자인팀 구역」** | 마크업, JS |
| **기능 추가팀** | 마크업의 지정 앵커 주석 자리<br>`</script>` 직전 **「기능팀 구역」** | 기존 CSS 규칙, 데이터 줄 |

### 두 팀 공통 금지

1. **파일 전체 포매팅 금지.** Prettier·정렬·들여쓰기 일괄 변경을 한 번 돌리면
   4,589줄이 전부 충돌로 잡히고 상대 팀 작업이 통째로 막힙니다.
2. **데이터 줄 수정 금지.** 봇이 덮어쓰므로 고쳐도 다음 갱신 때 사라집니다.
   데이터가 틀렸으면 `open api/bake-*.mjs`를 고칩니다.
3. **외부 CDN 추가 금지.** 이 앱은 인터넷 없이도 열려야 합니다.
   검사(`test.js`)가 외부 호출을 잡아냅니다.

### 디자인팀에게

색은 `:root`의 토큰 하나만 바꾸면 전체에 반영됩니다.
토큰에는 **명암비 수치가 주석으로 적혀 있습니다**(예: `--leap-blue: #1B4FA0; /* 7.45:1 */`).
이 수치는 접근성 기준이므로 색을 바꿀 때 함께 확인합니다.
`test.js`가 학교급 색의 라이트·다크 양쪽 대비를 검사하며, 기준을 못 넘기면 배포가 멈춥니다.

다크 모드가 이미 있습니다. **라이트만 고치고 끝내면 다크가 깨집니다.**

### CSS를 별도 파일로 뺄 경우

`theme.css` 같은 파일을 새로 만들면
`사이트 굽기.command`의 124~129줄(파일을 하나씩 `cp`로 복사하는 자리)에도
**복사 한 줄을 추가해야 합니다.**
빠뜨리면 로컬에서는 되고 라이브에서만 스타일이 통째로 빠집니다.

## 4. 투입 순서

```
1단계  레이아웃 개편(사이드바 접기·지도 크게 보기·손조작)   ✔ 끝남 (2026-09-02)
2단계  협업 준비물 (PR 검사·CODEOWNERS·PR 템플릿·구역 주석)  ✔ 끝남 (2026-09-02)
3단계  기능팀이 새 꼭지의 «빈 골격»만 먼저 작게 머지         ← 지금 여기
4단계  디자인팀이 그 위에 스타일
```

**순서를 지키는 이유**: 골격이 바뀌면 그 위에 올린 스타일이 통째로 뒤집힙니다.
디자인을 먼저 하면 같은 작업을 두 번 하게 됩니다.

---

## 4-1. 갖춰 둔 준비물

| 무엇 | 어디 | 하는 일 |
|---|---|---|
| PR 검사 | `.github/workflows/pr-check.yml` | PR 이 열리면 배포 때와 «같은» 검사를 미리 돌립니다 |
| 리뷰어 자동 지정 | `.github/CODEOWNERS` | 파일별로 봐야 할 사람이 자동으로 붙습니다 |
| PR 서식 | `.github/pull_request_template.md` | PR 을 열면 아래 체크리스트가 저절로 뜹니다 |
| 디자인팀 구역 | `prototype/index.html` 의 `</style>` 바로 위 | 새 CSS 를 모으는 자리 |
| 기능팀 구역 | `prototype/index.html` 의 「8. 초기화」 바로 위 | 새 JS 를 모으는 자리 |
| 기능팀 자리(마크업) | 홈 화면 좌·우 칸에 주석으로 표시 | 새 꼭지를 넣을 자리 |
| 디자인팀 안내 | [08_디자인팀_색과_치수.md](./08_디자인팀_색과_치수.md) | 토큰이 네 벌·열일곱 벌인 사정과 명암비 기준 |

> **PR 검사는 켜 두었지만, «통과해야 머지된다»는 강제는 아직 없습니다.**
> Settings → Branches → main → "Require status checks to pass" 에서
> `검사와 굽기` 를 골라 주세요. 2절의 봇 bypass 설정도 이때 함께 합니다.

> ⚠️ **CODEOWNERS 에는 띄어쓰기가 든 경로를 적을 수 없습니다.**
> CODEOWNERS 는 규칙 다음의 «빈칸»부터를 사람 이름으로 읽습니다. 그래서
> `06. 실행계획(1)/prototype/index.html @누구` 라고 적으면 「06.」까지만
> 규칙으로 읽고 나머지를 이름으로 봅니다. 벗어나게 적는 방법도 없습니다.
> 대신 `**/prototype/index.html` 처럼 **띄어쓰기가 없는 형태**로 적습니다
> (`**/` 가 앞 폴더를 몇 겹이든 건너뜁니다).

## 5. PR 전 체크리스트

- [ ] `git pull --rebase origin main` 했는가
- [ ] `node "06. 실행계획(1)/prototype/test.js"` 가 전부 OK 인가
- [ ] 브라우저로 직접 열어 보았는가 (`열어보기.command`)
- [ ] 다크 모드에서도 확인했는가 (화면 오른쪽 위 «어두운 화면으로»)
- [ ] 인쇄 미리보기가 깨지지 않는가 («현재 화면 인쇄»)
- [ ] 내 구역 밖을 건드리지 않았는가
- [ ] 데이터 줄을 건드리지 않았는가

## 6. 사고가 났을 때

**라이브가 깨졌다**
→ `main`에서 문제 커밋을 `git revert` 하고 push 합니다. push 자체가 재배포입니다.
   되돌리는 편이 고쳐서 올리는 것보다 항상 빠릅니다.

**데이터 갱신이 안 돈다**
→ Actions 화면에서 경고를 봅니다. 공공데이터 서버가 GitHub 러너 IP를 막는 일이
   주기적으로 있고, 이때는 실패가 아니라 경고로만 남습니다(자세한 사정은
   `refresh-public-data.yml` 머리말에 적혀 있습니다).
   브랜치 보호 설정 때문이라면 2절의 bypass 를 확인합니다.

**충돌이 크게 났다**
→ 브랜치를 오래 들고 있었다는 뜻입니다. 되살리려 애쓰기보다
   `main`에서 새 브랜치를 따고 변경분만 다시 옮기는 편이 빠릅니다.
