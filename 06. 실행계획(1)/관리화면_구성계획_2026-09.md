# 관리 화면(마스터 계정) 구성 계획 · 뉴스 주기와 주제 조정

작성: 2026-09-06 · 대상: `team-leap-source`

이 문서는 세 가지 질문에 답합니다.

1. **주간 뉴스 주기를 매일·3일마다로 바꿀 수 있나. 요금이 나오나**
2. **뉴스 주제를 조정할 수 있나**
3. **코드를 몰라도 넣고 뺄 수 있는 「마스터 계정」을 만들려면 어떻게 해야 하나**

---

# 1. 뉴스 주기 — 바꿀 수 있고, 요금은 안 나옵니다

## 1-1. 결론

| 질문 | 답 |
|---|---|
| 주기를 바꿀 수 있나 | **예.** 한 줄 고치면 됩니다 |
| 매일 돌려도 되나 | **예.** 아래 세 가지 모두 여유가 큽니다 |
| 요금이 나오나 | **아니오.** 지금도, 매일로 바꿔도 무료 한도의 한 자릿수 % 입니다 |
| 자료가 망가지지 않나 | **안 망가집니다.** 8월 31일에 그 문제를 이미 고쳤습니다 (1-4 참고) |

## 1-2. 지금 얼마나 쓰고 있나 — 실제 기록

최근 30일 GitHub Actions 실행 기록을 세어 본 값입니다.

| 워크플로 | 횟수 | 평균 소요 |
|---|---|---|
| 공공데이터 정기 확인 및 갱신 | 38회 | 123.5초 |
| **주간 뉴스 받아오기 및 자동 배포** | **54회** | **22.0초** |
| PR 검사 | 8회 | 18.1초 |
| **합계** | **100회** | **총 100.4분** |

> 뉴스가 54회나 도는 것은 **일정 때문이 아닙니다.** `main` 에 커밋할 때마다
> 배포하려고 도는 것입니다(뉴스 수집은 그때 건너뜁니다).
> **일정으로 돈 것은 8/16 · 8/23 · 8/31 세 번**입니다.

## 1-3. 한도와 여유

### GitHub Actions

비공개 저장소는 **월 2,000분 무료**(Free 요금제)입니다. 과금은 **작업 하나당 1분 단위로 올림**입니다.

| | 월 실행 | 월 소모(올림) | 2,000분 대비 |
|---|---|---|---|
| 지금 (주 1회) | 100회 | 약 100분 | **5%** |
| **3일마다로** | +6회 | 약 106분 | **5.3%** |
| **매일로** | +26회 | 약 126분 | **6.3%** |

**매일로 바꿔도 무료 한도의 6%대입니다.** 요금이 나올 지점과는 거리가 멉니다.

### 네이버 검색 API

한 번 돌 때 **검색어 3개 × 1회 = 3번** 부릅니다(한 포털이 되면 다른 쪽은 안 두드립니다).

| | 하루 호출 | 무료 한도 | 사용률 |
|---|---|---|---|
| 지금 (주 1회) | 약 0.4회 | 25,000회/일 | 0.002% |
| **매일로** | **3회** | 25,000회/일 | **0.012%** |

## 1-4. 더 자주 돌려도 자료가 안 망가지는 이유

예전에는 **위험했습니다.** 히스토리를 «건수»로 잘랐기 때문입니다(`HISTORY_MAX = 60`).
하루에 서른 번 밀어 넣은 날 창이 **17일치에서 8일치로 줄었고**, 밀려난 기사 77건은
커밋 기록에서 되살려야 했습니다.

**8월 31일에 «날짜»로 자르도록 바꿨습니다.**

```
HISTORY_DAYS = 120     ← 120일 안의 기사는 남깁니다
HISTORY_MAX  = 500     ← 파일이 끝없이 커지지 않게 하는 안전장치일 뿐
```

이제 **몇 번을 돌리든 120일 창은 그대로**입니다. 주기를 올려도 안전합니다.

## 1-5. 오히려 «더 자주»가 나은 이유

검색어마다 **한 번에 최신 30건**만 받아옵니다(`display=30&sort=date`).

> 일주일 사이에 그 검색어로 31건이 넘는 기사가 나오면,
> **31번째부터는 영영 못 받습니다.** 다음 주에는 이미 창 밖으로 밀려나 있습니다.

지금 걸러진 뒤에도 하루 4~5건씩 쌓이는 것을 보면, 거르기 전 원본은 그보다 훨씬 많습니다.
**주 1회는 이미 놓치고 있을 가능성이 큽니다.** 자주 돌수록 촘촘해집니다.

## 1-6. 어떻게 바꾸나 — `.github/workflows/update-news.yml` 한 줄

```yaml
  schedule:
    - cron: '0 22 * * 0'     # ← 지금: 일요일 22시(UTC) = 월요일 07시(한국)
```

| 원하는 주기 | 고칠 값 | 한국시간 |
|---|---|---|
| **매일** | `'0 22 * * *'` | 매일 아침 7시 |
| **주 3회 (권장)** | `'0 22 * * 0,2,4'` | 월·수·금 아침 7시 |
| 주 2회 | `'0 22 * * 0,3'` | 월·목 아침 7시 |
| 하루 두 번 | `'0 22,10 * * *'` | 아침 7시 · 저녁 7시 |

> ⚠️ **`*/3` 은 쓰지 마세요.** `0 22 */3 * *` 은 「3일마다」가 아니라
> **매달 1·4·7…28·31일**입니다. 달이 바뀌면 간격이 1~2일로 찌그러집니다.
> 「3일마다」를 정확히 하려면 **요일 지정**(`0,2,4`)이 낫습니다 — 간격도 고르고
> 언제 도는지 사람이 예측할 수 있습니다.

### 알아 두실 것 — 일정은 «정시»에 안 돕니다

실제 기록입니다. GitHub 공용 러너가 붐비면 **밀립니다.**

| 예정 | 실제 | 지연 | 결과 |
|---|---|---|---|
| 8/16 22:00 | 22:16 | 16분 | **실패** |
| 8/23 22:00 | 22:17 | 17분 | 성공 |
| 8/30 22:00 | 8/31 00:10 | **2시간 10분** | 성공 |

- 아침 7시에 정확히 올라오길 기대하지 마세요. **7시~9시 사이**로 보시면 됩니다.
- **가끔 실패합니다**(8/16). 자주 돌수록 한 번 실패해도 다음 회차가 금방 옵니다 —
  이것도 주기를 올리는 편이 나은 이유입니다.

## 1-7. 부작용 하나 — 매일 배포됩니다

뉴스 워크플로는 수집 뒤 **사이트를 굽고 배포까지** 합니다.
매일로 바꾸면 **사이트가 매일 새로 배포됩니다.**

- 검사 3,365개를 통과해야만 나가므로 **위험하지는 않습니다.**
- 다만 배포 이력이 매일 쌓이고, 사람이 만든 변경과 봇 변경이 섞입니다.
- 신경 쓰이면 **주 3회(월·수·금)** 가 적당한 타협입니다.

# 2. 뉴스 주제 — 조정할 수 있습니다. 다만 «두 군데»입니다

여기가 헷갈리기 쉬운 부분입니다. **주제라고 부르는 것이 두 가지**입니다.

| | 무엇 | 어디 | 몇 개 |
|---|---|---|---|
| **① 검색어** | 네이버에서 **무엇을 가져올지** | `fetch-news.js` | **3개** |
| **② 화면 주제** | 가져온 것을 **어떻게 나눌지** | `prototype/index.html` | **6개** |

**①을 안 고치고 ②만 늘리면 그 칸은 늘 비어 있습니다.** 안 가져온 것은 나눌 수 없습니다.

## 2-1. ① 검색어 (가져오는 것)

```js
const QUERIES = ['소규모학교 통폐합', '학령인구 감소 학교', '경북 학령인구'];
```

- 하나 늘릴 때마다 **호출 3회 → 4회**(한도의 0.016%). 늘려도 됩니다.
- ⚠️ **「학령인구 감소」처럼 넓은 말만 넣으면 안 됩니다.** 실제로 그렇게 했다가
  문구회사 실적·대학 평가 등급 기사가 잔뜩 왔습니다.

## 2-2. 점수와 잡음 거르개 — 검색어보다 이쪽이 중요합니다

가져온 기사는 **점수**로 거릅니다.

```js
5점  경북·포항·경주… (이 대시보드는 경북 것이므로 가장 무겁게)
3점  폐교·통폐합·적정규모·분교·소규모학교
2점  학교·교육청·학급·교원·초등·중학교·고등학교·유치원
1점  학령인구·저출생·지역소멸·인구감소
```

> 경북 가중치가 **3이었을 때 경기도 포천 기사가 경북 기사와 같은 점수로 묶여**
> 카드 넉 장 중 셋이 포천이 된 적이 있습니다. 그래서 5로 올렸습니다.

그리고 **잡음 거르개**가 있습니다 — `주가·증시·코스닥·실적·매출·대학평가·아파트·분양…`
전부 실제로 걸려 나왔던 것들입니다.

**새 주제를 넣을 때는 점수표와 잡음 거르개도 함께 봐야 합니다.**

## 2-3. ② 화면 주제 (나누는 것)

```js
['통폐합·적정규모', /폐교|통폐합|통합 ?운영|적정규모|분교|학교 ?통합/],
['교육재정',       /교부금|재정|예산|교육재정/],
['교원·정원',      /교원|정원|교사 ?수|배치 ?기준|공무원 ?정원/],
['통학·돌봄',      /통학|스쿨버스|돌봄|기숙/],
['지역소멸·인구',  /지역소멸|인구감소|소멸위험|저출생|저출산|학령인구/],
['교육혁신·특구',  /교육발전특구|교육혁신|미래교육|늘봄/]
```

한 줄 더하면 주제가 하나 늘어납니다. 예를 들어:

```js
['다문화·특수교육', /다문화|중도입국|외국인가정|특수교육|특수학급|통합교육/],
['폐교 활용',       /폐교 ?활용|폐교 ?재산|유휴 ?교실|매각/],
```

- 기사 하나가 **여러 주제에 걸칠 수 있습니다** — 그래서 주제별 합이 건수보다 큽니다
  (화면에도 그렇게 적혀 있습니다).
- 주제를 늘리려면 **①의 검색어도 함께** 늘려야 그 칸이 찹니다.

## 2-4. 지금 구조의 불편함 — 3장의 출발점

주제 하나를 바꾸려면 **자바스크립트 파일 두 개를 열어 정규식을 고쳐야 합니다.**
이건 코드입니다. 데이터팀·디자인팀에게 「여기 정규식 고치세요」라고 할 수는 없습니다.

**그래서 3장의 관리 화면이 필요합니다.**

# 3. 마스터 계정(관리 화면) — 구성 계획

## 3-1. 먼저: 백엔드가 «꼭» 필요하지는 않습니다

「관리 화면 = 데이터베이스」라고 생각하기 쉽지만, **하려는 일에 따라 다릅니다.**

| 하려는 일 | DB 필요? |
|---|---|
| 뉴스 주제·검색어 넣고 빼기 | **아니오** |
| 뉴스 주기 바꾸기 | **아니오** |
| 화면 문구·기준일 고치기 | **아니오** |
| 지금 바로 수집 한 번 돌리기 | **아니오** |
| 사용자마다 다른 화면 보여주기 | 예 |
| 방문 기록·통계 쌓기 | 예 |
| 수집한 원본을 오래 보관·재현 | 예 |

**지금 원하시는 것은 전부 위쪽입니다.** 아래쪽(D1)은 나중 이야기입니다.

## 3-2. 결정적인 제약 — 지금의 안전장치를 깨면 안 됩니다

이 프로젝트의 안전은 **한 줄기**로 되어 있습니다.

```
고침 → 검사 3,365개 → 통과해야만 굽기 → 배포 → 라이브
            ↓ 실패하면
       사이트는 직전 정상본을 유지
```

그리고 모든 변경이 **git 이력**에 남아 `git revert` 로 되돌릴 수 있습니다.

> ⚠️ **관리 화면이 데이터베이스를 직접 고쳐 라이브를 바꾸면 이 줄기가 통째로 빠집니다.**
> 검사도 안 돌고, 이력도 안 남고, 되돌리기도 어렵습니다.
> 「편하게 고치려다 안전장치를 잃는」 맞바꿈이 됩니다.

## 3-3. 그래서 권하는 방식 — **설정을 파일로 빼고, 관리 화면은 그 파일을 고칩니다**

```
관리 화면(웹)  →  GitHub API 로 설정 파일 수정  →  커밋
                                                    ↓
                                          검사 3,365개 자동 실행
                                                    ↓
                                              통과하면 배포
```

**사람이 하던 일을 화면이 대신할 뿐, 안전장치는 그대로입니다.**
이력도 남고, 되돌리기도 되고, 잘못 넣으면 검사가 막습니다.

## 3-4. 3단계로 나눠 하기

### 1단계 — 설정을 한 파일로 모으기 〔가장 먼저 · 반나절〕

지금 흩어져 있는 것을 `config/news.json` 한 곳으로 모읍니다.

```json
{
  "검색어": ["소규모학교 통폐합", "학령인구 감소 학교", "경북 학령인구"],
  "주제": [
    { "이름": "통폐합·적정규모", "낱말": ["폐교","통폐합","적정규모","분교"] },
    { "이름": "교육재정",       "낱말": ["교부금","재정","예산"] }
  ],
  "잡음": ["주가","증시","코스닥","실적","매출","대학 평가","아파트","분양"],
  "보관일수": 120,
  "카드수": 4
}
```

- 정규식을 **낱말 목록**으로 바꿉니다 — 코드를 모르는 사람이 고칠 수 있게.
- `fetch-news.js` 와 대시보드가 **같은 파일**을 읽습니다(지금은 따로입니다).
- 검사를 답니다: 주제 이름 중복, 빈 낱말, 검색어 0개 등.

> **이 단계만 해도 「GitHub 에서 JSON 한 줄 고치기」로 주제를 바꿀 수 있습니다.**
> 관리 화면이 없어도 됩니다. 2단계는 그걸 더 쉽게 만드는 것뿐입니다.

### 2단계 — 관리 화면 〔1~2일〕

```
team-leap.pages.dev/admin/          ← 로그인해야 열립니다
  ├ 뉴스 설정      검색어·주제·잡음 낱말 넣고 빼기
  ├ 주기 설정      매일 / 주3회 / 주1회 고르기
  ├ 지금 수집      단추 하나로 즉시 실행
  └ 자료 상태      기준일·마지막 갱신 시각 보기
```

**어떻게 동작하나**

| 화면에서 | 실제로 일어나는 일 |
|---|---|
| 주제 추가 → 저장 | GitHub API 로 `config/news.json` 커밋 → 검사 → 배포 |
| 주기 변경 → 저장 | `update-news.yml` 의 cron 한 줄 커밋 |
| 「지금 수집」 | `workflow_dispatch` 로 워크플로 실행 |

**로그인은 Cloudflare Access 를 씁니다** — 직접 만들지 않습니다.

- Cloudflare Zero Trust → Access → Application 으로 `/admin/*` 을 감쌉니다
- 허용할 이메일(예: `@sc.gyo6.net`)만 적어 두면 그 사람만 들어옵니다
- **50명까지 무료**입니다
- 비밀번호를 우리가 보관하지 않습니다 — **유출될 비밀번호 자체가 없습니다**

**필요한 것**

| 무엇 | 왜 | 비용 |
|---|---|---|
| Cloudflare Access | 로그인 | 무료(50명) |
| GitHub Fine-grained PAT | 설정 파일 커밋용 | 무료 |
| Pages Function 2개 | 읽기·쓰기 중계 | 무료 한도 안 |

> PAT 는 **이 저장소·Contents 쓰기**만 주고 만료일을 짧게 둡니다.
> Cloudflare Secret 에만 넣고 Git 에는 이름만 남깁니다(지금 방식과 같습니다).

### 3단계 — D1 데이터베이스 〔필요해지면〕

**지금은 필요 없습니다.** 다만 밑준비는 이미 되어 있습니다.

| 이미 있는 것 | 무엇 |
|---|---|
| `backend/migrations/0001_initial.sql` | 표 7개 (출처·수집이력·학교·연도통계·인구전망·품질오류·버전) |
| `backend/wrangler.backend.example.jsonc` | D1·R2 바인딩 이름 |
| `functions/shared/data-catalog.js` | 자료 목록 |
| `backend/scripts/check.mjs` | 목록·스키마 검사 |

**언제 3단계로 가나** — 아래 중 하나가 생길 때입니다.

- 시군·학년별 자료가 들어와 **정적 파일로는 너무 커질 때**
- 수집 **원본을 보관해 나중에 같은 결과를 재현**해야 할 때
- 사용자마다 **다른 화면**을 보여줘야 할 때
- 방문·이용 **통계**를 쌓아야 할 때

## 3-5. 안 하시길 권하는 것

| 하고 싶어질 수 있는 것 | 왜 권하지 않나 |
|---|---|
| 관리 화면에서 **대시보드 숫자를 직접 고치기** | 자료는 공개 통계에서 옵니다. 손으로 고치면 출처와 어긋나고, 다음 수집 때 덮여 사라집니다 |
| 비밀번호 한 개로 로그인 | 새는 순간 끝입니다. 누가 고쳤는지도 모릅니다 |
| 설정을 DB 에만 두기 | 이력·되돌리기·검사가 전부 빠집니다 |
| 관리 화면을 대시보드 안에 넣기 | 공개 화면에 관리 코드가 섞입니다. **`/admin/` 으로 분리** |

## 3-6. 권하는 순서

```
① 설정 파일로 모으기 (config/news.json)      ← 반나절, 지금 바로
      ↓  이것만으로도 GitHub 에서 고칠 수 있게 됩니다
② 뉴스 주기 조정 (cron 한 줄)                 ← 5분
      ↓
③ 관리 화면 + Cloudflare Access              ← 1~2일, 팀 합류 뒤
      ↓
④ D1 백엔드                                   ← 필요해질 때
```

> **①과 ②를 먼저 하시길 권합니다.** ③이 없어도 「주제를 넣고 빼는」 일은
> ①만으로 됩니다. ③은 그걸 **웹에서** 하게 만드는 편의이고,
> 그 편의가 정말 필요한지는 ①을 한 달 써 보고 정하셔도 늦지 않습니다.
