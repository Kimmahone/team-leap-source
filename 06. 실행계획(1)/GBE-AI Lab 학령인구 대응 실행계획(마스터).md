### 1-2. 아직 비어 있는 것 (우리가 채울 자리)

1. **데이터가 없다.** 구성안의 표는 전부 예시 수치다. 실제 22개 시군 × 학교급 × 연도 데이터셋이 없다.
2. **예측 알고리즘이 없다.** "경북형 예측 모델 정립"이라고만 되어 있고, 어떤 방법으로 2036년 학생 수를 뽑을지 정의된 바 없다.
3. **동작하는 화면이 없다.** 구성안은 정지된 그림(이미지 PDF)이다. 필터를 눌러도 아무 일도 일어나지 않는다.
4. **역할 분담이 없다.** TEAM LEAP 10명 중 누가 대시보드를 맡는지 정해져 있지 않다.

→ **1, 2, 3번이 정확히 AI 활용 분과 연구원이 할 수 있고, 해야 하는 일이다.**

기획예산관은 12월에 **교육청 누리집에 정식 서비스를 개통**한다. 그건 정보센터 가상화 서버, DB 서버, 보안성 검토, 웹 접근성 인증이 붙는 공식 사업이다. 교사 동아리가 그걸 직접 구축할 수는 없다.


이 포지셔닝을 문서에 명시해 두면, 나중에 "왜 교사가 시스템을 만드냐"는 질문에 답할 수 있고, 거버넌스 분과가 걱정한 **행정적 권한 문제**도 피할 수 있다.

### 2-3. 예측 알고리즘 설계 (경북형 모델)

구성안이 요구하는 것은 단순 추세 외삽이 아니라 **정책 변수를 바꿔 볼 수 있는 시뮬레이터**다. 3단 구조로 간다.

#### 1단계 — 학생 수 예측: 코호트 진급법 (Cohort Survival)

```
S(y+1, g+1) = S(y, g) × r(g)          # g학년 → g+1학년 진급률
S(y+1, 초1)  = B(y+1-6) × e            # 6년 전 출생아수 × 취학률
S(y+1, 중1)  = S(y, 초6) × t_초중       # 초→중 진학률
S(y+1, 고1)  = S(y, 중3) × t_중고       # 중→고 진학률 (지역 유출 반영)
```

- `r(g)`, `t`는 최근 3~5개년 실적의 시군별 평균으로 산출
- 구성안 주석 "**지역간 학생 유입 및 유출을 배제함**"에 따라, 기본 모드는 유출입 0으로 두고 **유출입 보정을 옵션 토글**로 별도 제공
- 출생아수 확보가 어려운 시군은 D1(주민등록 연령별 인구)의 0~5세 코호트로 대체

#### 2단계 — 학급 수 산출

```
C(학교, 학년) = ceil( S(학교, 학년) / L )      # L = 학급당 학생수 기준
단, S < 복식기준 인 경우 인접 학년 통합 (복식학급)
```

`L`은 사용자가 선택한 기준에 따라 바뀐다.
- (a) 기준연도 실적 학급당 학생수 유지
- (b) `L = 입력값 ± 편차`
- (c) `학급당 N명 + 학년당 M학급` 상한 동시 적용

#### 3단계 — 학교 수 산출 (3개 시나리오)

| 시나리오 | 계산 | 정책적 의미 |
|---|---|---|
| (a) 학교 수 동결 | 학교 수 고정, 학급당 학생수만 하락 | "아무것도 안 하면" — 과소학교 급증 |
| (b) 학생수 감소율 연동 | `학교수 × (1 - 학생감소율)` | 비례 축소 |
| (c) 지정 감소율 | `학교수 × (1 - 입력 %)` | 정책 목표 대입 |

**출력 지표**: 학생수, 대비 감소율, 학급수, 학교수, 학급당 평균 학생수, **적정학교 수 / 최소학교 수 / 과밀·적정·과소 분류**

> 검증 방법: 2016년 실적을 기준연도로 넣고 2026년을 예측 → 실제 2026 실적과 오차율 비교. **백테스트 결과를 반드시 문서에 남긴다.** 이게 있으면 "교사가 만든 것"이 아니라 "검증된 모델"이 된다.

### 2-4. 기술 선택

| 영역 | 선택 | 이유 |
|---|---|---|
| 프론트엔드 | 단일 페이지 웹앱 (HTML/CSS/JS) | 별도 설치 없이 링크만으로 시연·공유 가능 |
| 지도 | **VWorld(국토지리정보원)** 또는 경북 시군 GeoJSON + SVG | 카카오/네이버 지도는 교육청 도메인 등록·쿼터·상용 라이선스 이슈. 공공 지도가 누리집 탑재에 안전 |
| 차트 | 경량 차트 라이브러리 또는 SVG 직접 | 외부 CDN 의존 최소화 (보안성 검토 대비) |
| 데이터 | 정적 JSON (프로토타입) → REST API (정식) | 데이터 소스 교체가 쉬운 구조 |
| 개발 방식 | 바이브 코딩 (생성형 AI 활용) | 계획서 명시 방식, 8월 집중 개발에 적합 |

**웹 접근성은 처음부터 지킨다.** 12월 개통 조건에 "웹 접근성 인증"이 명시되어 있다. 나중에 고치면 화면을 다시 짜야 한다.
- 색상만으로 정보를 전달하지 않는다 (과밀/적정/과소는 색 + 패턴 + 텍스트 라벨 병기)
- 모든 차트에 대체 텍스트 및 데이터 표 제공
- 키보드만으로 전체 조작 가능
- 명도 대비 4.5:1 이상

**개인정보는 다루지 않는다.** 학교 단위 집계만 사용한다. 학생 개인 식별 정보는 어떤 형태로도 프로토타입에 넣지 않는다. (동아리 계획서 초안에 "학급 내 학생 성별, 통학시간, 다문화" 데이터 요청이 있으나, 이는 대시보드가 아닌 교수·학습 앱 트랙 사안으로 분리하고 개인정보 영향평가 없이는 착수하지 않는다.)

## 3. 나머지 과제 배치

대시보드에 집중한다고 해서 나머지 과제를 버리는 것이 아니다. **비용이 다른 일**이므로 병렬로 돌린다.

### 과제① 학교 업무 자동화 1인 1앱 — 전원 / 저비용 병렬
7월에 이미 시작된 트랙. 각자 자기 업무 맥락의 앱 1개. 9월 시연회에서 취합.
- 생활지도: 상담 기록 정리, 학부모 소통 문안
- 교무: 보결 시간표 자동 편성, 계획서·공문 초안
- 학급: 가정통신문 번역, 뉴스 클리핑

### 과제② 교수·학습 혁신 앱 — 2~3명 / 10~11월 실증 집중
- 성취기준 기반 과정중심평가 루브릭 자동 생성
- 성취수준 분석 → 부진 학생 보충자료 생성
- 다문화 가정 학생 언어번역 지원

### 과제④ 교육용 웹앱스토어 — 11월 / TEAM NODE와 반드시 조율
**중복 위험 경보.** 참고용 계획서를 보면 다른 AI활용 동아리 **TEAM NODE**의 과제③이 "GBE-AI Lab 플랫폼 구축 및 운영"이다. TEAM LEAP의 과제④(웹앱스토어)와 사실상 같은 것을 두 동아리가 각각 만들 위험이 있다.

→ **8월 중 TEAM NODE와 조율 회의 1회.** 플랫폼 본체는 NODE, TEAM LEAP은 등록되는 콘텐츠(앱 + 사용법 + 프롬프트 + 활용사례)와 대시보드 공급으로 역할을 나누는 것이 합리적이다. 예산 항목 "웹앱스토어 운영 50만원"의 중복 집행도 함께 정리한다.
