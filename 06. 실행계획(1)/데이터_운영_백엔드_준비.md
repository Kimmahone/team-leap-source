## 결론

지금 바로 큰 백엔드를 만들 필요는 없다. 먼저 **누가 다시 실행해도 같은 데이터셋을 만들 수 있는 구조**를 만드는 것이 우선이다. API 키 자체가 아니라 원본 스냅샷, 변환 규칙, 검증 결과, 갱신 이력이 프로젝트 자산으로 남아야 담당자가 바뀌어도 유지된다.

## 권장 구조

현재 Cloudflare Pages를 유지한다면 다음 구조가 단순하다.

1. **GitHub Actions 또는 Cloudflare Cron**이 정해진 주기에 학교알리미·KOSIS·SGIS·유치원알리미를 수집한다.
2. 원본 응답은 **Cloudflare R2**에 날짜별로 보존한다. API가 바뀌거나 값이 수정돼도 이전 원본을 재현할 수 있다.
3. 정제된 학교·연도·지표는 **Cloudflare D1**에 저장한다. 화면이 필요한 범위만 Pages Function/Worker API로 조회한다.
4. 현재 정적 대시보드는 마지막 성공 데이터 스냅샷을 계속 사용한다. 새 수집이 실패해도 공개 화면이 비지 않는다.
5. 수집 성공·실패, 행 수, 누락 수, 원본 해시를 기록하고 이상이 있으면 배포하지 않는다.

## 최소 데이터 모델

| 테이블 | 핵심 필드 |
|---|---|
| `data_source` | source_id, 기관, API/통계표 ID, 주기, 라이선스, 담당자 |
| `ingest_run` | 실행시각, 대상연도, 상태, 원본위치, 원본해시, 행 수, 오류 |
| `school` | 표준학교코드, 학교명, 학교급, 설립유형, 주소, 행정코드, 좌표, 유효기간 |
| `school_stat_year` | 학교코드, 기준연도, 학생수, 학급수, 교원수, 특수학급 학생수 |
| `population_projection` | 지역코드, 기준/예측연도, 연령, 인구, 출처 버전 |
| `data_quality_issue` | 실행 ID, 자료, 심각도, 대상키, 문제, 처리상태 |

학교명은 바뀔 수 있으므로 이름이 아니라 **공식 학교코드**를 연결키로 사용하고, 시군도 행정표준코드를 함께 보관해야 한다.

## 단계별 추진

### 0단계 — 지금 할 일

- 현재 API/통계표 ID와 환경변수 이름을 데이터 목록표에 모은다.
- 수집 스크립트의 입력 연도·출력 파일·검증 명령을 문서화한다.
- 정적 데이터에 `source`, `reference_date`, `fetched_at`, `schema_version`을 붙인다.
- 운영 키는 모두 Cloudflare Secret으로 유지하고 저장소에는 이름과 재발급 절차만 남긴다.

### 1단계 — 재현 가능한 갱신

- 한 명령으로 `수집 → 정제 → 검사 → 정적 데이터 생성`이 끝나도록 만든다.
- 마지막 성공 스냅샷과 새 스냅샷의 차이를 자동 보고한다.
- 실제 운영 배포는 검사 통과 뒤에만 실행한다.

### 2단계 — 작은 운영 백엔드

- R2에 원본 스냅샷, D1에 정제 데이터를 저장한다.
- Pages Function에 `/api/data-version`, `/api/schools`, `/api/projections`처럼 읽기 전용 API를 둔다.
- 화면에 `자료 기준일·버전·마지막 갱신 상태`를 표시한다.

### 3단계 — 인수인계와 관리 화면

- 담당자가 데이터 갱신 상태, 오류, 이전 버전을 확인하는 내부 관리 화면을 둔다.
- 키 교체, 새 통계표 추가, 스키마 변경, 장애 복구 절차를 운영 매뉴얼로 만든다.

## 인수인계 전에 꼭 정할 결정

1. 누가 각 데이터의 공식 소유자·검수자인가
2. 갱신 주기와 공개 승인 절차는 무엇인가
3. 원본 API가 수정한 과거 값을 새 값으로 덮을지, 버전으로 남길지
4. 학교 단위 공개 가능 필드와 내부 전용 필드의 경계
5. 다른 연구팀 데이터와 연결할 공통키(학교코드·행정코드·기준연도)
6. Cloudflare·GitHub 조직 계정의 소유권, 후임자 권한, 비상 복구 담당자

## 현재 프로젝트에서 이미 갖춘 기반

- API 키를 정적 HTML에 넣지 않고 Cloudflare Secret과 Pages Function에서 사용한다.
- KOSIS 통계표 ID와 수집 스크립트, 학교알리미·유치원알리미·SGIS 수집 경로가 있다.
- 데이터 합계·중복·좌표·키 유출을 검사하는 자동 테스트가 있다.
- GitHub `main` 푸시 뒤 배포 저장소를 갱신하는 자동 배포 흐름이 있다.

다음 단계의 핵심은 새 서비스를 많이 붙이는 것이 아니라, 이 기반에 **원본 보존·버전·수집 이력·실패 시 이전 데이터 유지**를 추가하는 것이다.
